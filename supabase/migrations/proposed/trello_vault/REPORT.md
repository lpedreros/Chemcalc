## What the migration does
1. **Pre-flight** (reads `pg_class`/`pg_attribute`/`pg_proc`/`has_*_privilege`, never `information_schema`): the three Supabase roles exist; `trello_connected` exists and is a stored generated column (Migration A); Vault schema, `create_secret`, `update_secret`, `secrets`, `decrypted_secrets` exist and the running role may use them (including DELETE on `vault.secrets`); anon/authenticated hold no table-level UPDATE (`relacl`); no half plaintext pair; no half pair of ids; no id pointing at a missing secret; no profile with ids *and* plaintext.
2. Adds `trello_api_key_id`, `trello_token_id` (nullable uuid), each with a **unique index** so two profiles can never share a secret. (Not requested; one line each, dropped with the columns on rollback.)
3. Creates `trello_store_credentials(uuid,text,text) → boolean`, `trello_read_credentials(uuid) → table(api_key,token)`, `trello_clear_credentials(uuid) → boolean`. All `SECURITY DEFINER`, `search_path = ''`, fully qualified names, `FOR UPDATE` on the profile row. Return values are booleans so the handler can keep its `404 no_profile` answer. Each also checks its caller: `current_setting('role') = 'service_role'`, or a direct admin session (`role` = `none` and `session_user` in postgres/supabase_admin/service_role). This does not depend on JWT claims. `REVOKE ALL … FROM PUBLIC, anon, authenticated` by name, then `GRANT EXECUTE … TO service_role`.
4. Moves every profile holding both plaintext values (0..N, `order by id for update`): two Vault secrets, ids set, both plaintext columns nulled, read-back compared before moving on. Plaintext columns are **not dropped**.
5. `ALTER COLUMN trello_connected SET EXPRESSION AS (trello_api_key_id is not null and trello_token_id is not null)`, skipped on re-run. The post-flight proves `pg_class.relacl` and the column's `attacl` are byte-identical to before.
6. **Post-flight** raises (so nothing commits) if: any plaintext credential survives; any id pair fails to decrypt to two non-empty values; `trello_connected` disagrees with the ids; any function is executable by anon, authenticated or PUBLIC (checked with `has_function_privilege` *and* `aclexplode(proacl)`), or by any role other than service_role/owner/postgres/supabase_admin; a function is not SECURITY DEFINER with an empty search_path; the browser roles can write the id columns or `trello_connected` (they could otherwise point an id at someone else's secret); a table-level INSERT/UPDATE exists; `relacl`/`attacl` changed.

Vault 0.3.1 gaps, handled: no `delete_secret` → `clear` does `DELETE FROM vault.secrets` and re-checks the rows are gone. `update_secret` no-ops on a missing id → `store` only updates ids that exist in `vault.secrets`, creates a fresh secret otherwise, and always reads both values back, raising `XX000` on mismatch.

## Handler patch (item 2)
`readCreds` → RPC `trello_read_credentials`; `actionConnect` → RPC `trello_store_credentials`; `actionDisconnect` → read, RPC `trello_clear_credentials`, then the existing PATCH for the four board/list columns only. The credentials never go through a `profiles` request any more. Everything from the Trello section down to the end of the file, and the header types, are unchanged (a test asserts those sections are byte-identical to the deployed file).
One deliberate difference: if the pre-disconnect read fails with `db_error` (a stored secret that no longer decrypts), Disconnect proceeds with nothing to revoke instead of failing, otherwise a user with a corrupted connection could never clear it. Other read failures (503) still abort as before.

## The backout question you asked (rollback)
Restoring plaintext from Vault is **not hypothetical, it is the main job of the rollback**. The migration nulls the plaintext columns, and from the moment the patched function is live every new connection exists only in Vault. Dropping the id columns alone would silently disconnect everyone. `rollback.sql` copies each pair back (verifying each value), puts `trello_connected` back on its original expression *before* dropping the id columns it references, deletes the feature's secrets (including orphans named `trello_*:<uuid>`), drops columns and functions. It cannot recover a credential whose Vault secret is already gone: it refuses and changes nothing, and that user must reconnect after fixing.

## What I could not verify, and what could still go wrong
- **Real Vault.** Encryption, the `postgres` role's privileges on schema `vault`, and the real `decrypted_secrets` view are not reproduced. The migration pre-flight and `live_rehearsal_rolled_back.sql` check them against the real database; that is the first thing Sentinel's run should show.
- **PostgREST.** I assumed the role is visible as `current_setting('role')` inside a SECURITY DEFINER function (true in Postgres: `SET ROLE` is a session setting, definer switches only `current_user`). If it were not, the failure is closed: the function raises 42501 and the handler answers 500 `db_error`, no leak. The first post-deploy `boards` call from the QA session settles it (expect 409 `not_connected` for an unconnected user, 200 for Leo).
- **Not byte-compared** with the deployed handler (read only).
- **Real Trello** (the `connect` verify and token revoke) is faked, as in the existing tests.

## Open items and decisions for Leo / Sentinel
1. **Cut-over window.** Apply the migration, then deploy the Vault `handler.ts` straight away. In between, the old handler reads the now-null plaintext columns and every user sees "Trello is not connected" (nothing is lost). Rolling back is the mirror image: run `rollback.sql`, then redeploy the old handler.
2. **Dependency on Migration A.** This migration refuses to run unless `trello_connected` already exists. I did not check whether A has been applied (that would need a database query).
3. **Id columns are readable by their owner until Migration B**, because `authenticated` holds a table-level SELECT; RLS still limits it to the user's own row. They are opaque uuids useless without Vault access, and the browser cannot write them (asserted).
4. **Account deletion leaves orphans.** Deleting a user cascades to `profiles` but not to Vault, so their two encrypted secrets stay behind (plaintext used to disappear with the row). I did not build a trigger because the brief fixed the function count. Suggested follow-up, **untested**: a `BEFORE DELETE` trigger on `profiles` that deletes `vault.secrets` rows for `old.trello_api_key_id`/`old.trello_token_id`. `rollback.sql` already sweeps orphans by name.
5. **Migration B (item 6; not built, not touched).** When whoever owns it eventually runs the separate "Migration B" (revoke table-level SELECT from anon/authenticated, re-grant an explicit column list), it must first confirm `trello_api_key_id` and `trello_token_id` already exist, because this migration adds them. Note also: the version of B in this repo, `20261008130100_revoke_profiles_trello_secret_columns.sql`, has a pre-flight that refuses to run if `profiles` has any column it does not list, so after this migration it will stop on those two ids until they are deliberately left out of the grant (recommended: keep them hidden from the browser, which closes item 3).
6. After the live cut-over, Leo should Disconnect and reconnect Trello once, as already noted in the earlier report, so the old plaintext-era token is revoked at Trello and re-stored through the new path.
