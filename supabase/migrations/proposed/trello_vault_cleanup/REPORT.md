## The design changed from the one in the dispatch — and why (the finding)
The dispatch suggested a BEFORE DELETE trigger that calls `trello_clear_credentials(OLD.id)`. I tested that exact design (test "FINDING") and it fails, for two independent reasons, so I did not use it and did not touch that function's caller check:

1. **BEFORE DELETE + `trello_clear_credentials` errors, even for a direct SQL delete (Verified).** The function UPDATEs the profile row to null its ids; the row is being deleted in the same command, so Postgres raises `tuple to be deleted was already modified by an operation triggered by the current command`. The account deletion fails and nothing changes. For the emulated Admin-API session the caller check (item 3) fires first, so it fails there too, with a different message.
2. **AFTER DELETE + `trello_clear_credentials` silently does nothing (Verified).** The profile row is already gone, so the function's `select … for update` finds no row, returns `false` and deletes no secret. Direct SQL delete: no error, both secrets stay orphaned.
3. **The caller check also refuses the Admin-API path (Verified in the replica, premise Read).** Supabase's docs say `supabase_auth_admin` is "the Postgres role that is used by Supabase Auth to make requests to your database"; `admin.deleteUser` and the dashboard's Delete user button are executed by Auth, not by a service_role connection. That role is neither `service_role` nor in the function's allow-list (role `none` + session_user postgres/supabase_admin/service_role), so the function raises 42501 `service_role only`. I emulated the session with `SET SESSION AUTHORIZATION supabase_auth_admin`. I could not observe a real Admin-API delete (no live access), so this part rests on the docs sentence plus the emulation.

**What I built instead:** a dedicated SECURITY DEFINER trigger function `trello_cleanup_vault_on_profile_delete()` (empty `search_path`, `EXECUTE` revoked from public/anon/authenticated/service_role, uncallable as a plain function: Verified) that deletes only the secrets the deleted row references plus the two named after that profile's uuid, then re-checks they are gone and raises if not. The existing Vault functions and their ACLs are untouched (Verified: byte-identical `proacl`, grants and tables before/after).
**Why AFTER, not BEFORE (Verified):** with a competing BEFORE trigger that cancels the delete (`RETURN NULL`), a BEFORE cleanup deletes the secrets while the profile survives with dangling ids; the AFTER trigger never fires for a row that was not deleted.
**Failure behaviour (Verified):** if the Vault delete fails (simulated with a failing trigger on `vault.secrets`), the whole account deletion fails and nothing is half-deleted. I chose loud failure over swallowing the error, because swallowing keeps a deleted user's credentials silently. If you prefer deletions to always succeed, the alternative is to downgrade the `raise exception` to `raise warning`; say so and I will change it.

## What was tested (Verified, all on the replica)
- Deleting a connected account removes exactly its two secrets and leaves other users' secrets and their working credentials alone, via **direct SQL as postgres**, via **`supabase_auth_admin`** (emulated Admin API), and via **service_role deleting the profiles row** (PostgREST style). Other cascades (a table with `ON DELETE CASCADE` off `auth.users`) still happen.
- A profile with no Vault ids, an `auth.users` row with no profile at all, half a pair of ids, and a dangling id all delete without error and without touching any other secret. A three-user multi-row delete and the ordinary insert/update paths on profiles behave as before. `anon` and `authenticated` still cannot delete profiles.
- Migration: idempotent (3 runs, identical state, one trigger); one-time sweep removes secrets named `trello_api_key:<uuid>`/`trello_token:<uuid>` that no profile references and whose uuid has no profile, and keeps referenced, live-profile-named and unrelated secrets; refuses with nothing changed when the Vault migration is missing, the running role lacks DELETE on `vault.secrets`, or does not own `profiles` (with a positive control that a non-superuser owner holding the grants applies it); its own post-flight catches a mutation that leaves `EXECUTE` on the function and one that makes the trigger BEFORE.
- Rollback: removes only the trigger and function, snapshot equals the pre-migration state, idempotent; afterwards deletes orphan secrets again, and re-applying sweeps them.
- Rehearsal script on the replica (with and without connected profiles): ends in `REHEARSAL_ROLLBACK (deliberate, nothing committed)`, every line `ok`, state unchanged, no credential value in output or notices; with a sabotaged trigger it reports `REHEARSAL_FAILED` instead.

## Not verified / limits
- No real Admin-API `deleteUser` was run (no live access): see item 3 above. **First live check after any apply:** create a throwaway user, connect Trello with a throwaway credential via the function (or skip), delete the user through the Admin API, confirm the two secrets are gone and the call succeeded.
- The rehearsal cannot exercise the Admin-API path: `postgres` on Supabase cannot become `supabase_auth_admin` from the SQL editor. It exercises a direct delete cascade on the real database (throwaway `auth.users` rows, rolled back). It assumes inserting `(id, email)` into `auth.users` works there; if not it prints a `--` skip line and stops that check rather than failing.
- Replica limits are the same as for the Vault migration (stand-in Vault, no PostgREST/GoTrue); the replica's `supabase_auth_admin` is a superuser stand-in only so the test helper can switch back (see the comment in `deleteAs`).
- Not covered by any row trigger, by Postgres design: `TRUNCATE public.profiles`, and sessions with `session_replication_role = replica`.
- Existing orphans: the sweep reports a count only. Whether any exist on the real database I did not check.
